## 2. Your question: do we need to save sessions?

**No — retire the session-log system.** Validated:

- Transcripts are already auto-saved as JSONL in `~/.claude/projects/<project>/` (sessions.md). `/resume`, `claude --continue`, `/branch` reopen them.
- `/rewind` (Esc Esc) restores code and/or conversation from a checkpoint created on every prompt (checkpointing.md). **Caveat:** it does not track Bash-made changes — git remains the real safety net.
- Auto memory is on by default and carries learnings across sessions (memory.md; first 200 lines/25KB load each session).
- Community: no source praises automatic per-session logs; the trend is a short on-demand **handoff/progress file** (Pocock `handoff`, Superpowers progress file).
- The one legitimate gap: transcripts are deleted after **30 days** (`cleanupPeriodDays`, default 30). For beginners, a one-line setting fixes that better than markdown logs.

**Can saving be automatic?** Yes, two honest options:
1. **Auto-checkpoint commit** — a `Stop`/`SessionEnd` hook that makes a *local* WIP commit (or `git stash`-style snapshot) when files changed. Never pushes. `/save` stays the deliberate "back it up to GitHub" verb.
2. Leave it to `/rewind` + git and teach `/save` well. (Simpler; my recommendation for v3.0, add #1 only if users lose work.)

## 3. Gaps for "beginners building enterprise software"

The framework protects the *editing loop* but not the *delivery pipeline* — which is what makes software enterprise-grade. Missing (my analysis, grounded against Anthropic's first-party tooling):

| Gap | Why it matters | First-party / standard answer |
|---|---|---|
| No CI | Checks only run on the builder's laptop; nothing stops a broken merge | GitHub Actions template: lint + typecheck + tests + build on every PR |
| No security review step | Beginners can't spot auth/injection bugs | Built-in `/security-review`; `anthropics/claude-code-security-review` Action (README: only for trusted PRs) |
| No dependency / secret scanning | Most real breaches are deps and leaked keys | Dependabot + `npm audit`/`pip-audit` + gitleaks in CI |
| No branch protection guidance | `/save` pushes straight to the current branch, often `main` | Teach "branch → `/share` PR → CI green → merge"; protect `main` |
| No coverage target | "Tests pass" can mean one trivial test | Coverage threshold in CI |
| No native permission rules or sandbox | Homemade guard is leaky (§1 #4–7) | `permissions.deny` for `.env*`/keys + `/sandbox` (off by default) |
| No independent reviewer | Same context that wrote the code reviews it | Reviewer subagent (`.claude/agents/`) or built-in `/code-review`, fresh context |
| No verification recipe | Claude can't prove the app runs | Built-in `/verify` + `/run-skill-generator` |
| No decision record | Enterprise buyers ask "why was it built this way" | Lightweight ADR template/skill |
| No production basics | Logging, error handling, env/config, migrations, rollback | Short rules files (path-scoped), not long CLAUDE.md prose |

### Stronger models → less scaffolding

Anthropic, verbatim:
- "If your prompts were designed to reduce undertriggering… these models may now overtrigger. The fix is to dial back any aggressive language." (prompting best practices)
- "Instructions like these cause over-verification on Claude Opus 5… The same applies to legacy harness scaffolding that adds separate verification steps." (Opus 5 prompting)
- "Every component in a harness encodes an assumption about what the model can't do on its own… strip away pieces that are no longer load-bearing." (harness-design blog)
- "Plan mode… adds overhead… If you could describe the diff in one sentence, skip the plan." (best-practices)
- "When there's something that absolutely must not happen, an instruction is the wrong tool." (steering blog) → use hooks/permissions.

Community agrees: heavy frameworks "burn 10x more tokens" and inject "noise in context" (HN, Superpowers/GSD thread).

**Rule for v3:** *hooks enforce only the things that must never happen; skills teach on demand; CLAUDE.md stays short and calm.* Remove reminders (plan reminder, naming/line-count nags, "think before coding"); keep hard blocks (secrets, bypassing checks, FDD structure).

## 5. Proposed v3 roadmap

| Phase | Scope | Size |
|---|---|---|
| **v2.4 — Fix what's broken** (safe, no redesign) | §1 #2–8, 10–17, 19–21: `$CLAUDE_PROJECT_DIR`, `jq` parsing, `permissions.deny` for secrets, fix commit gate (`git add &&` + flag forms), surface warnings via JSON `additionalContext` / exit 2, `stop_hook_active`, Notification event, gitignore + settings merge, rename `/design`, update model text | Small–medium |
| **v3.0 — Platform-native** | Plugin + marketplace; commands → skills; delete session logs + version-check + `/update`; tests/typecheck as `asyncRewake` on changed files; `init` skill for CLAUDE.md/rules/permissions; trimmed CLAUDE.md template; delegate to `/verify`, `/code-review`, `/security-review` | Large |
| **v3.1 — Enterprise foundation** | CI template (lint/type/test/build/coverage), security-review Action, Dependabot + gitleaks, branch-protection walkthrough, reviewer subagent, ADR skill, path-scoped production rules (logging, errors, config, migrations) | Medium |
| **v3.2 — Teach well** | README rewritten for auto mode, `/rewind`, `/resume`, `/goal`, plan-mode-when-it's-worth-it; plugin eval suite (`claude plugin eval`) to prove the framework helps | Medium |

## Residual risks / open questions

- Live in-session behaviour of hooks not observed (docs are explicit, but a 10-minute live test before v2.4 ships is cheap).
- Reddit not read.
- Windows/PowerShell users: Bash matchers miss the PowerShell tool — decide whether Windows is supported.
- Plugin route needs an end-to-end install test from a clean machine before committing to v3.0.
- Whether to keep FDD enforcement as default-on for beginners is a product decision, not a technical one.
